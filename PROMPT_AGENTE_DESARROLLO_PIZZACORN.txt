## 6. REGLA OBLIGATORIA NO-CONST

Los widgets de `pizzacorn_ui` nunca deben construirse con `const`, porque pueden leer tokens configurables en tiempo de ejecución.

Si un widget padre contiene un componente de `pizzacorn_ui`, no declares ese padre como `const` cuando ello fuerce a tratar el subárbol Pizzacorn como constante.

Incorrecto:

```dart
const Column(
  children: [
    TextBody("Hola"),
  ],
)
```

Correcto:

```dart
Column(
  children: [
    TextBody("Hola"),
  ],
)
```

## 11. BARREL DE IMPORTACIÓN ÚNICA

En proyectos de aplicación, cada archivo Dart debe importar únicamente:

```dart
import 'package:nombre_proyecto/config/imports.dart';
```

`lib/config/imports.dart` debe exportar los paquetes, modelos, estados, controladores, páginas, widgets, funciones y servicios necesarios.

Antes de añadir un import directo a un archivo, expórtalo desde el barrel.

Excepción: no apliques esta regla internamente al propio paquete `pizzacorn_ui` cuando produzca ciclos de importación. En el paquete, respeta su arquitectura real.


## 12. CONVENCIONES DE CÓDIGO

- Código: inglés.
- Comentarios: español.
- Variables y métodos: `lowerCamelCase`.
- Clases: `UpperCamelCase`.
- Constantes globales: `UPPERCASE_SNAKE_CASE`.
- Archivos: `snake_case.dart`.
- No uses prefijos privados con `_` en código Pizzacorn nuevo.
- Una variable que contiene un modelo debe terminar en `Model`.
- Una lista debe ser plural o terminar en `List`.
- Conserva UTF-8. Nunca introduzcas mojibake.
- Los comentarios deben ser breves y útiles; pueden usar emojis para identificar bloques.
- No comentes código obvio.

Bucles prohibidos:

```dart
items.forEach(...);

for (final item in items) {
}
```

Bucle obligatorio:

```dart
for (int i = 0; i < itemList.length; i++) {
  // 🔁 Procesamos el elemento conservando el índice.
}
```


## 13. CONSTRUCTORES Y PASO DE DATOS

Los widgets y funciones propias deben usar parámetros nombrados:

```dart
UserWidget({
  required this.userModel,
  this.onTap,
});
```

Si un widget necesita datos de una entidad, recibe el modelo completo:

```dart
UserWidget(
  userModel: userModel,
)
```

Evita pasar campos independientes del mismo modelo:

```dart
UserWidget(
  name: userModel.name,
  image: userModel.image,
)
```

La excepción son los modelos: sus constructores no deben usar parámetros `required`.


## 14. MODELOS

Toda lectura de Firebase debe convertirse en una clase modelo.

Un modelo debe incluir, adaptado a su esquema real:

- Constructor sin parámetros `required`.
- Valores predeterminados.
- `factory fromJson`.
- `toJson()`.
- `toJsonCreate()`.
- `toJsonUpdate()`.
- `copyWith()` completo.

Valores predeterminados habituales:

```dart
String name = "";
int quantity = 0;
double price = 0;
bool active = false;
List<String> tags = const [];
Map<String, dynamic> metadata = const {};
DateTime createdAt = DateTime(2000);
```

Adapta cada valor al tipo real del campo.

Fechas:

- Usa `parseDate` de `pizzacorn_ui`.
- Si no existe un valor válido, devuelve `DateTime(2000)`.

Serialización:

`toJson()`:

- Incluye el mapeo normal de los campos.

`toJsonCreate()`:

- Incluye los campos necesarios para crear el documento.
- Sustituye `createdAt` y `modifyAt` por `FieldValue.serverTimestamp()` cuando esos campos existan realmente.

`toJsonUpdate()`:

- Elimina `id`.
- Elimina `createdAt`.
- Sustituye `modifyAt` por `FieldValue.serverTimestamp()` cuando exista.

No asumas que todos los modelos comparten campos o fechas. Confirma el esquema real antes de implementarlos.


## 15. RIVERPOD

Las pantallas con lógica propia se dividen normalmente en:

- `nombre_state.dart`
- `nombre_controller.dart`
- `nombre_page.dart`

### State

La clase de estado debe ser inmutable e incluir como mínimo:

```dart
final bool isLoading;
final String isError;
```

Valores iniciales:

```dart
isLoading = false;
isError = "";
```

Debe implementar un `copyWith` completo.

### Controller

Usa `StateNotifier<NombreState>` cuando sea el patrón vigente del proyecto.

Toda operación asíncrona debe:

1. Activar `isLoading`.
2. Limpiar el error anterior cuando corresponda.
3. Ejecutarse dentro de `try-catch`.
4. Actualizar el estado de éxito.
5. Guardar el mensaje de error en `isError`.
6. Desactivar `isLoading` tanto en éxito como en error.
7. Evitar actualizar el estado después de eliminar el controlador.

No mezcles lógica compleja de Firebase dentro de un widget.

### Page

La página debe ser un `ConsumerWidget`, salvo que exista una razón técnica comprobada para usar otro tipo.

Debe:

- Observar el provider.
- Obtener el controller.
- Mostrar `Loading(loading: state.isLoading)`.
- Reaccionar a `state.isError`.
- Delegar la lógica al controller.


## 16. ESTRUCTURA HABITUAL DE PÁGINAS

Cuando la pantalla contenga datos paginados y la arquitectura real lo permita, usa:

```dart
class ReservationsPage extends ConsumerWidget {
  ReservationsPage({super.key});

  @override
  Widget build(BuildContext context, WidgetRef ref) {
    final state = ref.watch(reservationsProvider);
    final controller = ref.read(reservationsProvider.notifier);
    final params = controller.getPaginationParams();

    return Scaffold(
      backgroundColor: COLOR_BACKGROUND,
      body: Loading(
        loading: state.isLoading,
        child: CustomScrollView(
          slivers: [
            ReservationsAppBar(),
            CupertinoSliverRefreshControl(
              onRefresh: () {
                return ref
                    .read(paginationProvider(params).notifier)
                    .refresh();
              },
            ),
            SliverPadding(
              padding: PADDING,
              sliver: SliverToBoxAdapter(
                child: Column(
                  crossAxisAlignment: CrossAxisAlignment.start,
                  children: [
                    TextTitle("Reservas"),
                    Space(SPACE_SMALL),
                    TextBody("Gestiona las próximas reservas."),
                    Space(SPACE_MEDIUM),
                  ],
                ),
              ),
            ),
            SliverPadding(
              padding: PADDING,
              sliver: SliverListCustom<ReservationModel>(
                params: params,
                itemPlaceholder: ReservationModel(),
                idExtractor: (reservationModel) {
                  return reservationModel.id;
                },
                itemBuilder: (reservationModel) {
                  return ReservationWidget(
                    reservationModel: reservationModel,
                  );
                },
              ),
            ),
          ],
        ),
      ),
    );
  }
}
```

No fuerces esta plantilla si la pantalla no contiene paginación o el proyecto utiliza una estructura distinta apropiada.

El AppBar específico de la pantalla debe vivir en un archivo independiente.


## 17. PAGINACIÓN FIRESTORE

Usa el sistema de `pizzacorn_ui`:

- `PaginationParams<T>`
- `paginationProvider`
- `PaginationController<T>`
- `SliverListCustom<T>`
- `SliverGridCustom<T>`

Ejemplo:

```dart
PaginationParams<UserModel>(
  collection: "users",
  limit: 20,
  identifier: "usersHome",
  fromJson: (data) {
    return UserModel.fromJson(data);
  },
  query: (query) {
    return query.orderBy("createdAt", descending: true);
  },
)
```

Reglas:

- `identifier` debe ser único y estable.
- Toda lista o grid debe recibir `itemPlaceholder`.
- Usa un modelo vacío como placeholder.
- La consulta debe corresponder al esquema real.
- Confirma los índices necesarios.
- Confirma si se usa `(default)` o una base Firestore con nombre.
- No asumas que existe un geohash ni campos auxiliares.
- El pull-to-refresh llama a `paginationProvider(params).notifier.refresh()`.
- No dupliques la lógica ya resuelta por `PaginationController`.
